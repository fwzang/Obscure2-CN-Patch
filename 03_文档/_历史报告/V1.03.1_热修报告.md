# 《Obscure II》汉化补丁 V1.03.1 热修报告

- **版本**：V1.03.1（V1.03 的热修）
- **日期**：2026-10-25
- **数据包**：未变更

---

## 一、V1.03 出了什么问题

用户在新装游戏上安装 V1.03 后：**贴图正常了，但字幕/字体乱码**。

现场日志（2026-10-25 19:16）给出了明确证据：

```
[FSTRICT] #1 确认字体 dst=16B4BAA0（严格集=1）
[FSTRICT] 跳过同规格非字体纹理 tex=16B4C880（严格集=1）   ← 重复几十次
[STAT]    fontBinds=344  swaps=344                        （V1.02 时为 9742）
```

**严格集只认出了 1 张字体图集**，而游戏真正在用的另一张（`16B4C880`）被当成普通图片跳过。
结果是绝大部分文字没有换成中文图集，仍用原版字形渲染 → 看起来就是乱码。
`swaps` 从 9742 掉到 344，正是"文字几乎没被替换"的直接证据。

结论：**严格判据方向对（贴图恢复了），但覆盖不全（漏掉了真实字体）。**

---

## 二、V1.03.1 怎么修

加入**绑定次数提升**：

> 宽松集（512×256 登记表）里命中、但不在严格集的纹理，
> 统计它在 stage0 的绑定次数；**超过阈值（默认 20 次）即提升为字体并替换**。

依据：字体图集每帧反复绑定，UI 图通常只绑一两次 —— 用**频次**区分二者，
不需要读顶点、不需要 Lock。

| 项 | 行为 |
|---|---|
| 阈值 | `O2_PROMOTE_N`（默认 20；设 0 关闭提升） |
| 兜底 | 严格集为空仍退回旧判据 |
| 总开关 | `O2_STRICT_FONT=0` 整体退回 V1.02 判据 |
| 日志 | `[FSTRICT] 提升 tex=... 为字体（stage0 绑定 N 次）` |
| 顺带 | `FONT_TEX_MAX` 32→128、`FONT_STRICT_MAX` 64→128，避免登记表淘汰挤掉真字体 |

预期效果：**贴图不再被误替换，文字也能正常替换**。

## 四、验证方法

1. 装完确认 `d3d9.dll` md5 = `16358d85…`
2. 启动，日志应出现：

```
[INIT] ===== V68_PROD 严格判定+绑定提升 =====
[FSTRICT] 严格字体判定 启用（O2_STRICT_FONT=0 关闭）
[FSTRICT] 绑定提升阈值 = 20 次（O2_PROMOTE_N 可调，0=关闭）
[FSTRICT] #1 确认字体 dst=0x...（严格集=1）
[FSTRICT] 提升 tex=0x... 为字体（stage0 绑定 20 次）      ← 关键行
```

3. 看字幕/UI 文字是否正常中文
4. 看浴室提示等贴图是否正常
5. `[STAT]` 里 `swaps` 应回到数千量级（不再是 344）

**如果文字仍然乱码**：说明提升阈值没来得及生效或该纹理绑定次数太少，
可用 `O2_PROMOTE_N=5` 降低阈值重试；仍不行则 `O2_STRICT_FONT=0` 退回 V1.02 判据（贴图问题会回来，但文字一定正常）。

## 五、教训

V1.03 的严格判据是从"1 个样本"外推的——只验证了"被误替换的纹理确实不是字体"，
没有验证"所有字体都能被认出来"。**判定规则收紧时，必须同时验证召回率**，
否则就是修好了误报、引入了漏报。这次靠日志里 `swaps` 从 9742 掉到 344 才发现。
