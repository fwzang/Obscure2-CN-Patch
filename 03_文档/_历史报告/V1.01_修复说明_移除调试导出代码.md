# V1.01 修复说明：移除发布版残留的调试导出代码

> 问题由用户实测发现：游戏运行后，游戏目录出现 `font_dump.png`、`tex_16af7200.png` 等贴图文件。

---

## 1. 现象

游戏结束后，游戏目录残留若干 PNG：

```
font_dump.png          112,443 B   （游戏字库 512×256）
tex_16af7200.png       112,443 B   （同一张图，按纹理地址命名）
tex_16c7cb20.png       112,443 B
tex_16ccd4a0.png        32,072 B
tex_2104dd80.png        32,072 B
```

实测图片内容 = 拉丁字母/数字表 + 手柄按键图标，即**原版字体纹理**。

## 2. 根因

`d3d9_proxy.c` 中开发阶段（v39/v40/v41/v42）的诊断函数，被写在了
`#if G3_DIAG` 的 **`#else`（也就是生产）分支**里：

```c
#if G3_DIAG
    ... 只打日志 ...
#else                       /* ← 生产路径，反被塞了导出代码 */
    if (g_bigTex) {
        ...
        if (!g_fontDumped) { g_fontDumped = 1; dump_font_tex((void*)tex); }  /* 写 font_dump.png */
        ...
        dump_tex_once((void*)tex, ...);   /* 写 tex_<地址>.png，每个 512×256 候选各一张 */
```

三处副作用：

| 函数 | 引入 | 行为 |
|---|---|---|
| `dump_font_tex()` | v39 | 首次绑定字体纹理时，导出 `font_dump.png` |
| `dump_tex_once()` | v42 | 每个不同的 512×256 候选纹理导出一次 `tex_<hex地址>.png`（上限 24 张） |
| `stack_dump()` / `bind_use()` | v40/v41 | 纯日志，不产文件（一并清除） |

另外 `dump_font_tex()` / `dump_tex_once()` 还会 `LoadLibraryA()` 依次尝试 14~24 个
`d3dx9_*.dll` —— 发布版每次启动都白做一轮 DLL 加载尝试。

**为什么 V1.00 没被发现**：文件是在游戏目录生成的，不在 %TEMP%，且不影响画面，
只有细看目录才会注意到。二进制层面可验证：v47 内含 `font_dump.png` / `D3DXSaveTextureToFileA` /
`d3dx9_43.dll` / `DUMPTEX` 四个特征串。

## 3. 修复

物理删除，不是加开关 —— 发布版里不该存在写文件的能力。

| 步骤 | 内容 |
|---|---|
| 备份 | `d3d9proxy_src/d3d9_proxy.c.bak_v47` |
| 剥离 | `_verify/strip_diag_v48.py`（108 行）+ `_verify/strip_diag_v48b.py`（49 行） |
| 纠偏 | 误删 `g_last3DFrame` 定义（1506/1508 生产代码在用），已恢复 |
| 编译 | `ziglang cc -target x86-windows-gnu -O2 -shared -DDRAW_UNBIND=1`，零警告 |
| 自检 | 17 个诊断符号零残留；13 个生产符号全部在位 |

源码 1,878 行 → 1,830 行；DLL 1,084,928 B → 1,083,904 B。

**二进制终检**（`grep -a` 直搜字节）：

| 特征串 | v47 | v48 |
|---|---|---|
| `font_dump.png` | **FOUND** | clean |
| `D3DXSaveTextureToFileA` | **FOUND** | clean |
| `d3dx9_43.dll` | **FOUND** | clean |
| `DUMPTEX` | **FOUND** | clean |

**渲染逻辑零改动**：被删的三个函数只写文件 / 打日志，不触碰任何 D3D 渲染状态，
`g_dtPtr` 等数组也仅供它们自己使用。所以画面表现与 V1.00 完全一致，不需要重新验证汉化效果。
